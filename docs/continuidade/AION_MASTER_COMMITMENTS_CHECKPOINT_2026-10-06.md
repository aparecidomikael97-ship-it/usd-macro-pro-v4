# AION Master Commitments Checkpoint — 2026-10-06

Status: MASTER DESIGN CHECKPOINT / NO MERGE OR DEPLOY AUTHORITY

## 1. Priority order

Priority #1 remains the official AION Core V1 closure.

The Core must finish as a minimal, stable, auditable and governance-focused nucleus. New product capabilities must attach to AION through governed modules, permissions, policy boundaries, durable evidence and receipts rather than repeatedly reopening the frozen Core.

No feature defined in this checkpoint authorizes a Core merge, production deployment or privileged action by itself.

## 2. Core closure rule

Do not trade Core integrity for feature speed.

The official closure path remains fail-closed and separate. Any module in this checkpoint that depends on identity, authorization, external effects, receipts, persistence or owner decisions must consume those Core guarantees after they are properly closed.

If a capability can remain outside the frozen Core, it should.

## 7. Owner Advisor / second-brain behavior

AION should act as a decision-support partner for HUMAN_OWNER.

Examples:
- "AION, o que você acha desse valor?"
- "Essa empresa vale a pena?"
- "Qual é o risco desse contrato?"
- "Nossa capacidade aguenta esse cliente?"
- "Qual pacote faz mais sentido?"

AION should:
- gather available evidence;
- separate facts, estimates, hypotheses and unknowns;
- analyze margin, effort, capacity, risk, fit and strategic value when available;
- compare options;
- identify missing information;
- state confidence;
- recommend a next step;
- warn proactively when evidence shows material risk.

AION may advise strongly. It must not silently transform advice into owner-reserved execution.

## 14. Six ecosystem operating principles added today

### 14.1 Revenue before expansion
New features should not outrun the need to prove customer value and recurring revenue.

### 14.2 Proof of value per customer
Each real customer should have baseline, objective, KPI, evidence of delivered value and periodic review.

### 14.3 Operational simplicity
Prefer fewer reliable workflows over a large fragile feature surface.

### 14.4 Resilience and offline fallback
Critical demos, learning, owner guidance and safe local functions should degrade gracefully when connectivity fails.

### 14.5 Audit every external effect
Any action that changes an external system should have attribution, request evidence and outcome receipt. Ambiguity must never be silently converted into success.

### 14.6 Owner Control Center
AION should eventually surface a concise HUMAN_OWNER dashboard showing:
- cash and runway;
- revenue and margin;
- active customers;
- retention/health;
- pipeline;
- operational capacity;
- legal/tax/formalization pending items;
- brand/IP pending items;
- security/compliance alerts;
- unresolved external-effect outcomes;
- decisions requiring HUMAN_OWNER;
- top three priorities now.

The goal is decision clarity, not dashboard overload.

## 15. Transition-from-CLT operating objective

The ecosystem should support a safe transition rather than chase an arbitrary date.

The preferred path remains:
1. close Core;
2. stabilize AION Negócios;
3. obtain paying customers;
4. prove repeatable delivery and retention;
5. build recurring net income and reserve;
6. evaluate CLT exit only with objective evidence.

Trader should not be treated as the primary funding source for the transition. Negócios is the intended first cash engine; Investimentos is primarily preservation/long-term capital.

## 16. Change discipline

For any new idea:
1. determine whether it belongs in frozen Core or a governed module;
2. prefer governed module unless it is a true Core invariant;
3. define authority and risk boundary;
4. define evidence/receipt requirements;
5. isolate in Draft/CI-only work until appropriate;
6. do not merge/deploy without the required authorization;
7. do not let non-essential work displace official Core closure.
