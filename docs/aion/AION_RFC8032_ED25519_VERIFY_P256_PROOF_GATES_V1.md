# AION — Ed25519 RFC 8032 Public Signature Verification and TPM P-256 Proof Gates V1

**PREPARE: real mathematical signature verification of public test vectors
only. Not production trust, authenticated HUMAN_OWNER, verified collector,
TPM attestation, certificate enrollment or installation.**

## What this PR actually implements
- Ed25519 **detached public signature verification**, using the open-source
  `cryptography==50.0.2` package from ephemeral GitHub CI. Only
  `Ed25519PublicKey.from_public_bytes(...).verify(signature, message)`.
- Three RFC 8032 §7.1 official **public** key, message and detached
  signature vectors (TEST 1 zero-byte, TEST 2 one-byte, TEST 3 two-byte).
  **Official PRIVATE KEY/SECRET KEY fixtures are deliberately omitted.**
- Reject malformed/upper-case hex, invalid lengths, wrong role, wrong
  caller-reported key/message fingerprint, substituted message/signature,
  and syntactically forged signature claims. Input message limit 4096 bytes.
- Optional role-specific adapter that verifies only **Ed25519 signatures
  of the 32-byte domain-separated role-intent digest** generated by
  the pure #1109 three-role design; owner and collector role domains
  remain separate. The production system must still verify the
  **origin/authenticity of the entire challenge transcript**; this
  module does not do so.
- A separate P-256/TPM **attestation requirements reviewer** always
  returns `HARDWARE_ATTESTATION_UNIMPLEMENTED_BLOCKED`, even if
  passed a self-declared EK certificate, TPM flag, ECDSA signature or
  the successful Ed25519 test-vector result.

## What a mathematically valid Ed25519 signature proves
The detached signature is valid for **the exact bytes and public key
provided**. It does NOT prove that the supplied public key has ever
been pinned by a trusted HUMAN_OWNER, that the owner owns/custodies
that private key, that a collector is independent, that the signature
was authorized for an action, that the nonce is fresh, or that a
protected trust anchor exists.

The `claimed_public_key_sha256` input is a **caller claim**, NOT an
independent root of trust. Matching its SHA256 to caller-supplied
public bytes does not establish HUMAN_OWNER identity.
The strongest state is
`PUBLIC_KEY_SIGNATURE_MATHEMATICALLY_VALID_UNTRUSTED`, with every
authorization and physical proof boolean hard-coded FALSE.

A **valid RFC test vector** is not a production authorization,
because RFC public keys are public and are not trusted AION
enrollment keys. The test suite contains no private seed, does not
create keys and does not sign a transcript.

## P-256 TPM evidence: proof checklist only

The following are **independent requirements**, not measured facts:
1. Verified TPM manufacturer endorsement key certificate chain or a
   properly pinned endorsement public key (trust policy dependent).
2. Attestation key (AK) cryptographic trust bound to that TPM/EK.
3. Genuine TCG TPM2_Certify or alternative verifiable mechanism
   binding the exact P-256 public key and TPM attributes.
4. Curve, restricted/sensitive data and policy attributes validated.
5. Proof that private key is TPM-originated, fixed/nonexportable
   under the approved usage and authorization policies.
6. Verify attestation signature using an independent parsing/crypto
   implementation; never infer from KSP name or success status.
7. Bind fresh challenge nonce, collector/policy binary digest and
   device to the attestation; durable spent-nonce replay prevention.
8. Verified owner trust anchor, key replacement/compromise recovery,
   revocation and durable antirollback.
9. Negative vectors for malformed TPM2B/TPMS structures, altered
   public area, quote substitution and fake certificate chains.
10. Physical 12/12 sandbox and 16/16 network-deny witness evidence.

**No TPM commands, EK/AK reads, P-256 public key retrieval, certificate
requests or physical Windows probes occur in this PR.**
In particular, Microsoft's enterprise CA TPM key attestation
documented pathway only supports **RSA keys** and cannot automatically
serve as ECDSA P-256 attestation evidence.

## Dependency and provenance
CI uses `cryptography==50.0.2`, the current pinned release validated
for this test run. It is installed **only on disposable GitHub
Windows/Linux runners**, never on owner machine `am12`.
A pinned version is not a fully reproducible artifact by itself;
future production qualification must include pinned wheel hashes,
SLSA/provenance review, SBOM, supported OS ABI and offline package
verification. No production dependency or deployment was authorized.

## Strict rollout stop conditions
#1109 dual Ed25519 owner/collector and optional P-256 host signatures
still requires **independently enrolled and trusted public keys**, a
separate external Ed25519 custody decision and proof, real signed
role-specific transcript, fresh owner authorization, authorized
collector custody, durable nonce ledger and monotonic policy state.

#1049 sandbox proof 12/12 and #1087 network-denial 16/16 are
still **physically unverified**. No private keys, enrollment, owner
device read, Windows registry/TPM/ACL/WFP changes, merge to main,
installer build/deploy, spending or safe-to-resume from this PR.
