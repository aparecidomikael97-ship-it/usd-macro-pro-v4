# AION Chat — Mathematical Signed Turn Review V1 (NO AUTHORIZATION)

**Date:** 2026-10-09 | **Stack:** Draft #1120 (durable pending user turn) → this proposed Draft.  
**Default:** no provider, no billing, no model invocation, no model output, no owner enrollment.

## Deliverable

`review_signed_pending_model_turn(store, scope, access, ..., envelope,
host_public_pin, expected_policy_generation)` is a deliberately read-only
boundary for checking a detached Ed25519 signature over an *exact* future
model approval intent.

It uses the existing `aion_chat.models.Scope`,
`atlasquant_aion_chat_product_bridge.validate_product_binding`, the scoped
message rows genuinely staged by Draft #1120, and the preflight contracts of
Draft #1119. No second login/chat provider/storage system is introduced.

1. Checks the trusted host's pre-existing authenticated scoped ADMIN session;
   **this is NOT independent HUMAN_OWNER attestation**.
2. Reads existing nonarchived conversation and existing
   `Message(role='user', approval_state='PENDING')`; requires the canonical
   #1120 request digest, fixed row ID, exact source-message hash and no
   attachments or overwritten/stale approval flag.
3. Requires an exact, versioned closed-schema payload with owner/tenant/
   workspace, conversation, message, SHA-256 of *final prompt bytes*,
   provider/model/lane, positive integer max cost in USD microunits,
   independent expected policy generation and a 256-bit nonce.
4. Requires the host to inject a public `owner_key_id` and exact 32-byte
   Ed25519 public key, **separately** from the signed payload. The function
   will reject any attempt to add approval flags to that pin structure.
   Key provenance is NOT authenticated by this function.
5. Checks RFC8032 Ed25519 mathematics over UTF-8 canonical JSON with
   `sort_keys=True`, closed field list and explicit domain separator
   `ATLASQUANT_AION_CHAT_OWNER_MODEL_APPROVAL_V1\x00`. No private key
   is imported or generated by the production module. Keys are ephemeral
   only in the disposable CI test file.
6. Produces at most `SIGNED_TURN_MATH_VALID_UNTRUSTED`, never
   `APPROVED` or `CAN_CALL_MODEL`. Its digest is for forensic correlation
   and is NOT a protected receipt or antirollback attestation.

The model's proposed final prompt must be **byte-for-byte identical** to
the prompt the eventual execution adapter would send. No execution adapter
is connected by this PR. `build_provider_prompt` may truncate upstream and
must undergo separate end-to-end review before any real integration.

## Independent physical and operational blockers (always FALSE)

- No verified key enrollment or assurance that this key belongs to HUMAN_OWNER.
  **Supplying a fake new host pin together with a matching new private
  signature will yield valid *mathematics*, not real authorization.**
- No protected nonce issuance, no consumption/tombstone, no secure trusted
  clock, no policy-generation durable witness. Two identical signatures are
  both valid math results. Replay prevention is NOT implemented here.
- No simultaneous durable budget reservation, balance reconciliation or FX
  verification. Micro-USD is a signature-binding integer, not authorization
  to debit the R$200 infrastructure ceiling.
- No signed collector witness or TPM host key. Existing V3 witness #1116 is
  simulation and not integrated with this stack.
- No actual provider call, no billed request, no assistant response, no
  Streamlit UI flag, no production PostgreSQL, no voice, no desktop commands,
  no owner computer access or model download.

## Threat matrix exercised in disposable runners

- Key substitution, wrong public key, malformed detached signature and
  spoofed signer role/purpose.
- Swapping tenant, workspace, owner, conversation, staged message, exact
  prompt, provider, model, route, nonce, price cap, policy generation.
- Invalid types, unknown fields/claimed authorizations, false/zero costs,
  fractional currencies and malformed hashes.
- Forged pending state or changed stored text after signature.
- Duplicate signed intent: signature stays mathematically valid, while
  all replay, billing and execution gates remain false.
- Positive counterpart: a complete, correctly signed test fixture is
  recognized **only** as an untrusted mathematical candidate.
- No external network / billing using mock session guard.

## Nonnegotiable before enabling a provider

A separate **HUMAN_OWNER-approved rollout** must enroll identities and
pin trustworthy public keys, bind authenticated/attested owner intent
out-of-band, issue and consume nonces durably with the trusted monotonic
witness, atomically reserve budget, bind selected model/prompt bytes after
redaction, handle unknown provider outcomes without replaying a paid call,
and persist/model-label any result as `MODEL_OUTPUT_UNVERIFIED`.
Any unresolved issue is a hard NO-GO.
